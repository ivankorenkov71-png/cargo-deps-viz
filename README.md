# cargo-deps-viz

Инструмент визуализации графа зависимостей пакетов Rust (менеджер
пакетов Cargo). Готовые менеджеры пакетов и библиотеки для получения
зависимостей не используются.

## Параметры

| Опция | Описание | По умолчанию |
|---|---|---|
| `-p`, `--package` | имя анализируемого пакета (обязательно) | — |
| `-r`, `--repo` | URL репозитория или путь к тестовому файлу | `https://index.crates.io` |
| `-t`, `--test-mode` | режим работы с тестовым репозиторием | выключен |
| `-o`, `--output` | имя файла с изображением графа (`.svg`) | `graph.svg` |
| `-f`, `--filter` | пакеты с этой подстрокой в имени не учитываются | пусто |
| `--order` | вывести порядок загрузки зависимостей вместо графа | выключен |

## Функции

- `parse_args` — разбор опций командной строки.
- `check_package`, `check_repo`, `check_output`, `check_filter` —
  проверка каждого параметра, при ошибке выбрасывают `ValueError`.
- `validate_args` — запуск всех проверок.
- `index_path` — путь к файлу пакета в индексе crates.io
  (`serde` → `se/rd/serde`, `syn` → `3/s/syn`).
- `download_index` — скачивает файл пакета из репозитория
  (модуль `urllib` из стандартной библиотеки Python).
- `choose_version` — выбирает самую новую не отозванную версию.
- `direct_deps` — прямые зависимости версии без dev- и optional-.
- `fetch_deps` — всё вместе: имя пакета → список зависимостей.
- `read_test_repo` — читает тестовый репозиторий из файла.
- `get_deps` — зависимости пакета из файла (тестовый режим) или из сети.
- `is_filtered` — нужно ли пропустить пакет по подстроке фильтра.
- `bfs` — обход в ширину с рекурсией: один вызов — один уровень графа.
  Уже обработанные пакеты пропускаются, поэтому циклы не страшны.
- `build_graph` — строит полный граф (с транзитивными зависимостями).
- `print_graph` — выводит граф в виде `пакет -> зависимости`.
- `visit` — обход в глубину: пакет записывается только после всех
  своих зависимостей; находит циклы.
- `load_order` — порядок загрузки и список найденных циклов.
- `print_order` — выводит пронумерованный порядок загрузки.
- `main` — точка входа.

## Откуда берутся данные

Используется разреженный (sparse) индекс crates.io — тот же, что
читает сам Cargo. Для каждого пакета там лежит текстовый файл,
в котором каждая строка — JSON с описанием одной версии и её
зависимостей, например <https://index.crates.io/se/rd/serde_json>.

## Тестовый репозиторий

В тестовом режиме (`--test-mode`) вместо URL указывается путь к
текстовому файлу, где пакеты называются большими латинскими буквами.
Одна строка — один пакет и его прямые зависимости через пробел:

```text
# комментарий
A: B C
B: C
C:
```

Готовые файлы в папке `examples/`: `simple.txt` (3 пакета),
`big.txt` (10 пакетов, 4 уровня), `cycle.txt` (цикл A → B → C → A),
`self.txt` (пакет зависит сам от себя), `bad.txt` (ошибка в файле).

## Запуск и тесты

Нужен Python 3.8 или новее, сторонние библиотеки не требуются.

```bash
./run.sh -p serde_json
python3 -m unittest discover tests
```

## Примеры

```bash
./run.sh -p serde_json            # прямые зависимости serde_json
./run.sh -p serde_json -f derive
./run.sh -p A -r examples/simple.txt --test-mode
./run.sh -p A -r examples/big.txt -t -f G   # без пакета G
./run.sh -p A -r examples/cycle.txt -t      # цикл не мешает
./run.sh -p A -r examples/big.txt -t --order  # порядок загрузки
./run.sh -p serde_json --order
./run.sh -p serde -o graph.png   # Ошибка: нужен .svg
```

## Сравнение с Cargo: порядок загрузки

Настоящий Cargo показывает порядок сборки, если собрать любой
проект в один поток (строки `Compiling ...` идут по порядку):

```bash
cargo new demo && cd demo
cargo add serde_json
cargo build -j 1
```

Почему результаты могут отличаться:

1. Порядок загрузки не единственный: пакеты, которые не зависят
   друг от друга (`itoa` и `memchr`), можно ставить в любом порядке.
   Cargo к тому же собирает их параллельно.
2. Cargo собирает только то, что нужно для текущей платформы.
   У `serde_json` зависимость `serde` объявлена под условием
   `cfg(any())`, которое никогда не выполняется, поэтому Cargo её
   не собирает, а наша программа условия не читает и показывает её.
3. Cargo подключает необязательные (optional) зависимости, которые
   включены «фичами» по умолчанию (например, `aho-corasick` и
   `memchr` у `regex`). Наша программа optional-зависимости пропускает.
4. Наша программа всегда берёт самую новую версию пакета, а Cargo
   подбирает версию по требованию (`^1.0`) и может держать сразу
   две версии одного пакета (например, `syn` 2.x и 3.x).
5. Перед пакетами со скриптом сборки (`build.rs`) Cargo сначала
   собирает и запускает сам скрипт — в нашей модели этого шага нет.
